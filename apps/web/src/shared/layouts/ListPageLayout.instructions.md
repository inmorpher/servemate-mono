# ListPageLayout — расширенные инструкции по применению

## Назначение

Этот компонент предназначен для унификации структуры всех страниц-списков в приложении. Он отвечает за:

- общий контейнер страницы;
- мобильный и десктопный режим отображения фильтров;
- область контента;
- нижний футер, если он нужен;
- будущую общую верхнюю панель страницы.

## Когда использовать

Использовать этот лейаут для страниц, где есть:

- список сущностей;
- фильтры;
- табы;
- поиск;
- пагинация;
- карточки или таблица как основной вид отображения.

Подходит для разделов вроде:

- заказы;
- пользователи;
- каталог;
- категории;
- любые страницы со списком и фильтрацией.

Не использовать для:

- одиночных страниц без списка;
- форм;
- детальных карточек;
- экранов с одной основной сущностью без повторяющегося списка.

## Базовая структура

Лейаут должен быть построен по следующей схеме:

1. Верхняя часть страницы
    - заголовок;
    - описание/подсказка;
    - кнопки действий;
    - возможно, переключатель вида.

2. Блок активных фильтров
    - чипы выбранных фильтров;
    - возможность убрать фильтр одним действием;
    - кнопка очистки всех фильтров.

3. Панель инструментов
    - сортировка;
    - переключатель вида;
    - быстрые действия;
    - количество элементов.

4. Основной контент
    - таблица, список или карточки;
    - табы, если нужны;
    - пагинация/подвал списка.

## Рекомендуемый контракт для будущего расширения

Компонент должен оставаться универсальным и принимать данные извне, а не знать о конкретных бизнес-логиках.

### Основные пропсы

- filters — блок фильтров;
- content — основной контент списка;
- footer — нижний блок, например пагинация или дополнительные действия.

### Будущие расширения

В перспективе можно расширить пропсы, чтобы лейаут поддерживал:

- header — верхний блок страницы;
- title — заголовок;
- description — подзаголовок;
- actions — кнопки справа;
- activeFilters — список активных фильтров;
- onRemoveFilter — обработчик удаления фильтра;
- onClearFilters — обработчик очистки всех фильтров;
- viewMode — текущее состояние отображения (список/карточки);
- onViewModeChange — переключение вида;
- toolbarActions — дополнительные кнопки/действия.

## Как применять на странице

### 1. Оборачивать страницу в ListPageLayout

На странице списка нужно получать ее содержимое и передавать в лейаут как отдельные части:

```tsx
<ListPageLayout filters={<FiltersPanel />} content={<ListContent />} footer={<PaginationBlock />} />
```

### 2. Вынести все специфичное в feature-слой

На уровне страницы следует оставлять только:

- данные;
- состояние фильтров;
- состояние табов;
- обработчики;
- специфичные UI-блоки.

Сам лейаут не должен содержать бизнес-логику конкретной страницы.

### 3. Держать верхнюю часть страницы общей

Если страница использует общий заголовок, его лучше давать через единый интерфейс, а не создавать отдельные варианты в каждом месте.

Это помогает:

- не дублировать интерфейс;
- единообразно вести страницы списка;
- быстрее добавлять новые разделы.

## Рекомендации по UX

### Заголовок страницы

Заголовок стоит показывать почти на всех страницах-списках, особенно если у раздела есть табы. Это помогает пользователю сразу понять:

- где он находится;
- что именно сейчас отображается;
- какие действия доступны.

### Чипы активных фильтров

Чипы должны быть:

- компактными;
- легко удаляемыми;
- понятными по смыслу;
- расположенными прямо над списком или под верхней панелью.

### Переключатель вида

Если в разделе возможны несколько представлений, переключатель вида лучше делать общим и универсальным. Например:

- список;
- карточки;
- компактный режим.

### Кнопки действий

Кнопки действий стоит размещать в верхней панели, но делать их опциональными. Это позволит использовать лейаут и для простых списков, и для сложных каталогов.

## Поведение на мобильных и десктопе

- Фильтры на мобильных — через выдвижную панель.
- Фильтры на десктопе — в боковой панели.
- Верхняя панель и toolbar должны быть адаптивными.
- На маленьких экранах кнопки действий лучше сворачивать или переносить.

## Правила реализации

- Не перегружать лейаут бизнес-логикой.
- Делать блоки опциональными.
- Сохранять единый визуальный язык для всех страниц-списков.
- Сначала добавлять общие блоки, потом — специфичные для конкретного раздела.
- Не делать отдельные костыли для каждой страницы, если это можно выразить через общий интерфейс.

## Рекомендуемый порядок внедрения

1. Добавить заголовок страницы.
2. Добавить блок активных фильтров с чипами.
3. Добавить toolbar с кнопками действий и переключателем вида.
4. Подключить этот блок к существующим страницам-спискам.
5. Постепенно убирать дублирующиеся локальные решения.

## Краткая цель будущего состояния

Цель — сделать так, чтобы каждая страница-список выглядела одинаково по структуре и при этом оставалась гибкой для специфики конкретного раздела.

То есть:

- одинаковая оболочка;
- одинаковый UX для фильтров и действий;
- разная бизнес-логика внутри.
