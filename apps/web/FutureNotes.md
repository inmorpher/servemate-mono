# Заметка: добавить паттерн "parallel routes + portal" для использования табов и компонента <Activity/>

Цель

- Позволить рендерить панель Activity внутри UI-области табов, сохранив независимые маршруты и состояние (параллельные маршруты), при этом монтируя визуально в нужную точку DOM через React Portal.

Краткий план работ (шаги)

1. Проектирование

- Описать UX: как открывается/закрывается Activity, поведение при переключении табов, URL-структура.
- Решить: Activity как отдельный маршрут (route) + портал для визуальной отрисовки в TabLayout.

2. Создать параллельные маршруты (App Router)

- Выделить сегмент/группу для табов (например, app/(dashboard)/…).
- Добавить параллельный маршрут для activity (named parallel route) чтобы он рендерился вместе с основным контентом, но имел свой URL.
- Убедиться, что layout поддерживает отображение обоих деревьев одновременно.

3. Реализовать Portal target в Tab Layout

- В TabLayout добавить элемент-контейнер (например <div id="tab-portal-root" />) куда будет монтироваться Activity.
- Контейнер должен быть в клиентском компоненте (use client) — порталы рендерятся на клиенте.

4. Создать Portal provider / утилиту

- Небольшая обёртка/хук для создания и управления целевым элементом портала (createPortalTargetIfMissing, usePortal).
- Обеспечить SSR-совместимость: рендер основного контента на сервере, монтирование портала только на клиенте.

5. Реализовать Tabs компоненты

- TabsLayout с контейнером портала и зонами для табов.
- API: открытие/закрытие Activity через навигацию (push/replace) на route activity.

6. Реализовать компонент <Activity/>

- <Activity/> — клиентский маршрутный компонент, который монтируется через Portal в табы.
- Должен принимать props/state из URL (id, mode) и работать через существующие хуки (типы из @servemate/dto).
- Учитывать lazy-loading и состояние загрузки.

7. Синхронизация состояния и навигация

- Использовать router.push/replace для открытия activity (чтобы URL отражал состояние).
- При закрытии — возвращаться к предыдущему маршруту без потери контекста таба.
- При необходимости использовать useSearchCriteria / существующие хелперы для синхронизации параметров.

8. Вопросы SSR и гидрации

- Пометить компоненты как client-only.
- Минимизировать мерцание: показывать skeleton/placeholder пока портал не смонтирован.

9. Доступность и UX

- Обеспечить фокус-перемещение при открытии/закрытии Activity.
- Поддержать клавиатурную навигацию и aria-атрибуты в табах.

10. Тесты и документация

- E2E-тесты сценариев: открытие/закрытие, переключение табов, back/forward в истории.
- Документировать новую структуру маршрутов и пример использования в README фичи.

Критерии завершения

- Activity открывается по отдельному URL и визуально монтируется внутри табов.
- Переходы работают корректно с историей браузера.
- Нет SSR-ошибок/мерцаний, доступность соблюдена.
- Типы TypeScript покрывают контракт (использовать @servemate/dto).
